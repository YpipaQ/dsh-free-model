## 二、A 档：应做（3 条）

### A1. `77a0e87a` — buddy 续期保活（7 天主动续一次）

**本地确认：完全没有**（`buddy-auth.ts` 零命中）。

**缺陷**：CodeBuddy 的 `access_token` 有效期以**天**计（上游实测三批：60 / 30 / 28 天，在持续收缩），
而 lead-time 判据只在「距过期不足 1 小时」放行 ⇒ 调度器每 30 分钟一轮、**每轮都被跳过**
⇒ `refresh_token` 闲置 28 天被服务端**作废**：

```
POST /v2/plugin/auth/token/refresh → 401 {"code":12153,"msg":"refresh token is invalid"}
```

用户看到「凭据过期 / API 密钥无效」，面板写 `refreshable: false`，**只能重新登录**。

**为什么这是 A**：buddy 是本 fork 主力渠道之一（账本 3198 次调用），而这条修的是
「放着不用也会死」——**用户什么都不做，号就报废了**。

**改动量**：小。在 `shouldRefreshNow` 这条链上加一个「距上次成功续期 ≥ 7 天」的腿。

⚠️ **和本 fork 已有的改动有交互**：我们在 `expiry-sync.ts` 加了 `refreshExpiresAtOf`
（codearts 的 refresh 寿命腿）。这条是**同一个函数的第三条腿**，要写成「三腿取或」，
不能覆盖已有的。

### A2. `df6e9291` — zcode 营销/领取版本门槛 `3.17.1` → `3.18.2`

**本地确认：仍是 3.17.1**（`zcode-upstream.ts:111`）。

**缺陷**：ZCode 的营销活动只在 `GET /marketing/touch` 的 `deliveries` 里下发，服务端
**按活动、按 `X-ZCode-App-Version` 门控**（版本低 ⇒ `deliveries: []`，与「今天没活动」
**同形、零报错**；claim 端点同抬，版本低 ⇒ `1004 no permission`）。

门槛**逐期漂移**：1024 期 3.16.3、1103 期 3.17.1、**1120 期（ZCODE WEEKEND BUILD）抬到 3.18.2**。
现场报障「周末 5 亿又领不了」，根因就是常量停在上一期。

上游用 4 个真实账号只读实测（`GET /marketing/touch`，零领取零 captcha）：
`3.14.3…3.18.1` 全部 `deliveries` 空；**`3.18.2` 起拿到** `plan_id=zcode-v3-start-plan-wk-1120`、
`grant_units=500000000`。补丁级二分确认门槛**精确为 3.18.2**（3.18.1 空、3.18.2 即有）。

### ✅ 已核实：**安全，不触发 3012**

上游原文：「**推理路径版本（`ZCODE_INFERENCE_MIN_APP_VERSION`）未动，不触发 3012**」。

⇒ 这条改的是**营销/领取**路径的独立常量，**与 3.17 身份块无关**。
本评估第一版误以为要连身份块一起换，**已核实为不必**。

**改动量**：小。新增一个营销门槛常量（不要改 `ZCODE_INFERENCE_MIN_APP_VERSION`），
在其请求头里用它。

⚠️ 注意「同形」这个性质：**版本低时 `deliveries: []` 与「今天没活动」完全同形、零报错**
⇒ 用户和我方都无法从响应区分「没活动」与「版本太低」。这正是它拖了这么久才被发现的原因。

### A3. `43a00cdf` — codearts 目录完全走远端，静态兜底表退出目录路径

**本地确认：兜底表仍在用**（`llm-adapter.ts:1129` 的 `?? DEFAULT_MODELS`）。

**缺陷**：`DEFAULT_MODELS` 是**静态表，已腐坏**（上游明说「补 openpangu-2.1-pro /
glm-5.3-flash 是静态表腐坏的又一例」）。我们已经做过「目录自适应」（每日刷新），
但**兜底表本身仍是过期的**——远端拉不到时会退回它，用户看到一个含已下架模型的列表。

**为什么暂列 A 而不是立即做**：上游自己说「不能只是把 `?? DEFAULT_MODELS` 改成 `?? []`」——
一次试探性改动**连带红 7 条**，根因是 `syncCatalogEntries()` 是**同步契约**，
断掉兜底会让设置页 `total=0` ⇒ 整个 provider **误显示为「已关闭」**。

⇒ **这条要连 `syncCatalogEntries` 的同步契约一起设计**，不是一行改动。

### A4. `a95ac6d6` — minimax 余额必须带 `page_size`（否则**只算前 20 个包**）

**本地确认：完全同形**——`minimax-credits.ts:9` 用的正是 `GET /minimax-cloud/api/v1/credit/details`，
且**零分页参数**（`grep page\|offset\|limit` = 0 命中）。

**缺陷**（issue #141，真实账号实测）：该端点**默认只返回最近 20 个积分包**，函数把可见包的
`remaining_amount` 求和当余额 ⇒ **被挤出 20 条窗口的包，其额度从界面上消失**。

⚠️ **误差随天数单调扩大**（不是一次性偏差）：用户每天签到新增一个包（400 / 1000 分），
**最老的一个被挤出窗口** ⇒ 当被挤出的包余额接近新增包金额时，**界面总额彻底不动**。
这就是「明明显示签到成功、积分却不涨」的直接原因。

**修法**：`?page_size=1000`（上游实测 50 够用，但长期用户会再撞；
每天一个包 ⇒ 1000 天 ≈ 2.7 年）。**取大值一次性把窗口推远，不动架构。**

⚠️ 上游如实登记的**残余风险**：真超过 1000 个包仍会静默少算。根治要循环分页，
但 `page` 参数**未实测**（猜错会死循环，比现在更糟）⇒ 本轮不猜。
`total_count` 是唯一可用的自检点。

⚠️ 反向约束（上游守卫）：**只有 20 条时仍如实求和**，缺口**不得**编造或按均值外推 ——
余额要如实反映已知事实。
